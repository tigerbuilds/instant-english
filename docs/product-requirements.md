# 瞬間英作文 Web アプリ --- Product Requirements

- 作成日: 2026-10-07
- ステータス: Draft（Phase 0 完了時点）
- 対象バージョン: MVP

このドキュメントは Phase 0（要件定義）の成果物です。「何を作るか」「なぜ作るか」「何を作らないか」を定義します。技術選定（Phase 1）はこのドキュメントを根拠に行います。

---

## 1. 解決したい問題

英語で言いたいことはあるのに、「この文法で合っているか」の確認に時間がかかり、会話のテンポに乗れない。

既存の瞬間英作文教材は教科書的な文が中心で、学校・職場・友人との雑談で実際に自分が話すような口語表現を練習できない。また、自分の英語が自然かどうかを即座に判定してくれる相手もいない。

### このアプリの価値

正解を教えることではなく、**「まず出す → すぐ判定 → 次へ」という高速なサイクルを回させること**。ユーザーの課題は「文法を知らない」ではなく「正しさを気にして言葉が止まる」ことだからである。この視点を、機能の取捨選択の判断軸とする。

---

## 2. 想定ユーザー

### 一次ユーザー（MVP の対象）

開発者自身。

- 英語レベル: TOEIC 900 点、IELTS 7.0 程度。読み書きと文法知識は十分にあり、課題は発話の瞬発力。
- 英語を使う場面: 職場と学校の両方で雑談の機会がある。
- 学習時間: 1 回 15 分程度、毎日。
- 使用端末: ローカルの Windows PC（ブラウザ）。

### 二次ユーザー（将来の拡張候補）

一次ユーザーと似た境遇の中上級学習者。MVP では考慮しない。

### 設計方針

単一ユーザー前提。認証やユーザー管理は作らない。できるだけミニマルに進める。

### ユーザー像から導かれる制約

- 英語レベルが高いため、アプリが提示すべきは「正解」より「より自然な言い方」である。LLM への指示設計に直結する。
- 1 回 15 分のため、1 セッションで 10 問以上を素早く回せる UI が必要。1 問あたりの操作は最小限にする。

## 3. User Story

| ID | User Story |
|----|-----------|
| US-1 | 学習者として、会話で実際に使う自然な日本語表現を瞬間的に英訳したい。なぜなら、ライティングと違いスピーキングは瞬発力が勝負で、会話に特化した練習が必要だから。 |
| US-2 | 学習者として、回答に対するフィードバックを LLM からもらいたい。文法の正しさだけでなく、自然な表現になっているかも知りたいから。 |
| US-3 | 学習者として、毎日少しずつ、長く続けたい。なぜなら継続による反復が一番効くから。 |
| US-4 | 学習者として、回答のあと自分の英文と「より自然な言い方」を並べて見たい。なぜなら、差分を見ることで自分の癖に気づけるから。 |
| US-8 | 学習者として、どれだけ続けたか、どれだけ解いたかを見たい。なぜなら継続の実感がモチベーションになるから。 |

### 検討したが採用しなかった User Story

| ID | 内容 | 扱い |
|----|------|------|
| US-5 | 場面（職場・学校・友人）を意識した問題を解きたい | 将来候補 |
| US-6 | 起動後すぐに問題が始まり、1 問ごとの操作が最小限であってほしい | User Story ではなく非機能要件（NFR-4）として扱う |
| US-7 | 過去に間違えた表現を見返し、解き直したい | 将来候補 |

備考: US-8 は User Story としては採用したが、MVP には含めない（5 章参照）。

## 4. Core User Flow

ユーザーが最も頻繁に通る一本の道。画面構成と API の形はこの流れから決まる。

```text
1. アプリを開く
2. 日本語の問題文が表示され、タイマーが始まる
3. 英語を入力して送信する（時間切れなら、その時点の入力で自動送信）
4. 評価が表示される
   - 文法の指摘
   - 自然さの指摘
   - より自然な英文（自分の英文と並べて表示）
5. 「次へ」で 2 に戻る
```

- 解き直しは無し。流れは一直線。
- 制限時間: 初期値 30 秒。「文法を考える余裕はあるが、辞書を引く余裕はない」長さ。実際に使って調整する。
- 評価の長さ: 20 秒で読める量。指摘は最大 3 点、各 1 文。より自然な英文は 1 つ。

## 5. MVP に含める機能

MVP = 最小限の機能だが、実際に毎日使う価値がある版。

- 日本語の問題文を順に表示する。問題は開発者が自分で書いた固定リスト（職場・学校・友人の場面、30〜50 問）。
- 制限時間付きの英語入力。初期値 30 秒。時間切れは空欄でも自動送信。
- LLM による評価。文法の指摘、自然さの指摘、より自然な英文を自分の英文と並べて表示。
- 「次へ」で次の問題へ。

### MVP に関する重要な判断

- **LLM 評価を MVP に含める。** US-2 は問題定義の核であり、これが無い版を毎日使いたいとは思えないため。ただし開発は段階的に進め（UI → API → LLM 連携）、各段階で動くものを確認する。「開発の段階」と「MVP の定義」は別物として切り分ける。
- **Database を MVP に含めない。** 回答履歴や継続日数の表示（US-8）は MVP 後に回す。MVP は「何も記憶しないアプリ」であり、ブラウザを閉じれば回答は消える。
- **模範解答はすべて LLM が生成する。** 開発者が書くのは日本語の問題文のみ。LLM の出力品質に模範解答が依存するリスクがある（8 章参照）。

---

## 6. MVP に含めない機能（Out of Scope）

開発中に「ついでにこれも」と手を広げるのを防ぐため、明示的に列挙する。

- 回答履歴の保存（Database 全般）
- 累計問題数・継続日数の表示（US-8）
- 間違えた問題の復習・苦手表現の記録
- 場面の選択（職場・学校・友人を選んで出題する機能）
- 同じ問題の解き直し
- 問題の LLM 生成
- 複数ユーザー対応、ログイン、認証
- 音声入力・発音練習
- スマホ対応（PC ブラウザのみ）
- インターネット公開（ローカル PC で完結）

## 7. Functional Requirements（機能要件）

各項目は「できた／できていない」を判定できる文で書く。

### FR-1 問題の出題

- FR-1.1: アプリは、あらかじめ用意された日本語の問題文リストから 1 問ずつ表示する。
- FR-1.2: 問題文リストは、コードを変更せずに追加・編集できる形式で保持する。
- FR-1.3: 出題順はリストの記載順とする。
- FR-1.4: リストの末尾まで到達したら、先頭に戻って出題を続ける。

### FR-2 回答の入力

- FR-2.1: ユーザーは英語をテキストで入力し、送信できる。
- FR-2.2: 問題表示と同時に制限時間のカウントダウンを開始し、残り時間を表示する。
- FR-2.3: 制限時間の初期値は 30 秒とし、設定ファイル（問題リストと同じ場所）で変更できる。設定画面は作らない。
- FR-2.4: 時間切れ時は、その時点の入力内容（空欄を含む）で自動的に送信する。

### FR-3 回答の評価

- FR-3.1: 送信された英文を、ローカルで動く LLM に渡して評価する。
- FR-3.2: 評価結果は次の 3 要素を含む。文法上の指摘、自然さに関する指摘、より自然な英文。
- FR-3.3: 指摘は各 1 文、合計 3 点以内とする。
- FR-3.4: ユーザーの英文と「より自然な英文」を並べて表示する。
- FR-3.5: 空欄で送信された場合も LLM を呼び、「より自然な英文」を生成して表示する。指摘は省略する。

### FR-4 進行

- FR-4.1: 評価表示後、「次へ」で次の問題に進める。
- FR-4.2: 評価を待っている間、待機中であることを表示する。

## 8. Non-Functional Requirements（非機能要件）

技術選定の判断基準となる。

### NFR-1 コスト

- 開発・実行に必要な費用は 0 円。有料 API、従量課金、クレジットカード登録を必要とするサービスは使わない。
- LLM、Database、開発ツールはすべてローカル PC 上で動作する OSS または無料ソフトを使う。

### NFR-2 実行環境

- Windows 11 のローカル PC 上で、ブラウザから使用できる。
- インターネット接続は、初回のツール導入とモデル取得を除き不要。
- ハードウェア: AMD Ryzen 5 PRO 7545U（6 コア）、内蔵 GPU Radeon 740M（専用 GPU なし）、メモリ 16 GB。LLM の推論は CPU で行う。LLM に割り当てられるメモリは実質 8 GB 前後。

### NFR-3 性能（応答時間）

- 問題表示と「次へ」の遷移は体感で即時（1 秒未満）。
- LLM の評価は、送信から表示まで 15 秒以内を目標とする。CPU 推論のため、モデルの大きさ（3〜4B クラスか 7〜8B クラスか）と評価の質のトレードオフがある。Phase 8 で実測して見直す。

### NFR-4 使いやすさ

- 1 問あたりの操作は「入力」「送信」「次へ」の 3 つに収める。
- 15 分で 10 問以上回せること（1 問あたり制限時間 30 秒 + 評価待ち + 読む時間 20 秒 ≒ 60 秒）。

### NFR-5 保守性・学習性

- 使用技術は、開発者自身が仕組みを説明できるものに限る。
- 重要な技術選定は ADR として記録する。

### NFR-6 セキュリティ・プライバシー

- 秘密情報（将来の API Key など）は Git に含めない。
- MVP では個人情報を扱わない。

### 認識しているリスク

| リスク | 影響 | 対応方針 |
|--------|------|----------|
| CPU 推論のため LLM の応答が遅い | 「次へ」のリズムが崩れ、US-3（継続）を損なう | Phase 8 でモデルの大きさを実測して選ぶ。NFR-3 の目標値を見直す |
| 小さいモデルでは英語の指摘の質が粗い | US-2（自然さの判定）の価値が下がる | プロンプト設計で出力形式を絞る。必要なら速度を犠牲にして大きいモデルを選ぶ |
| 模範解答が LLM 生成に依存する | 不自然な模範解答を覚えてしまう可能性 | 中上級ユーザー自身が判断できる前提とする。将来、模範解答の手動登録を検討 |

## 9. 将来の拡張候補

優先度の高い順。US-3（続けたい）と US-8（記録を見たい）に近いものを上位にしている。

1. 回答履歴の保存（Database 導入）
2. 累計問題数・継続日数の表示（US-8）
3. 間違えた問題・不自然だった表現の記録と復習（US-7）
4. 場面（職場・学校・友人）による出題の絞り込み（US-5）
5. 学習進捗の可視化
6. 音声入力・発音練習
7. 他の学習者への公開（複数ユーザー対応、認証、クラウド公開）

---

## 10. 開発フェーズへの影響

要件定義の結果、当初の開発フェーズ案から次の点を変更する。

- Database（当初の Phase 7）は MVP に不要となったため、LLM 連携（当初の Phase 8）より後に回す。
- MVP の完成条件は「UI + API + LLM 連携」が動くこと。
