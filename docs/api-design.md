# API Design

- 作成日: 2026-10-19
- ステータス: Draft（Phase 6）
- 対象: MVP

画面（frontend）と裏側（backend）の間の取り決め。「どの URL に、どんな頼み方をすると、どんな返事が来るか」を定める。データの流れは `architecture.md` 3 章を参照。

---

## 1. 共通の決まり

- URL はすべて `/api/` から始める。画面の配信用の URL と混ざらないようにするため。
- 頼む側も返す側も JSON を使う。
- 文字コードは UTF-8。
- 裏側は `http://localhost:3000` で待ち受ける。
- 失敗したときは、HTTP のステータスコードで種類を示し、本文に理由を入れる。

失敗時の本文の形:

```json
{ "error": "question not found" }
```

| ステータス | 意味 | 例 |
|---|---|---|
| 200 | 成功 | |
| 400 | 頼み方が間違っている | 必要な項目が無い |
| 404 | 頼まれたものが無い | 存在しない問題番号 |
| 502 | 裏側のさらに裏（Ollama）が失敗した | Ollama が起動していない、返事の形が崩れた |
| 500 | それ以外の裏側の失敗 | |

## 2. 問題を 1 件取る

```text
GET /api/questions/{id}
```

### 頼み方

URL の `{id}` に問題番号を入れる。最初の 1 問は `1` を頼む。

### 返事（200）

```json
{
  "id": 3,
  "japanese": "それ、あとでメールで送っておくね",
  "nextId": 1
}
```

| 項目 | 型 | 意味 |
|---|---|---|
| `id` | number | この問題の番号 |
| `japanese` | string | 日本語の問題文 |
| `nextId` | number | 次に頼むべき番号。末尾の次は先頭に戻る（FR-1.4） |

### 失敗

| ステータス | いつ |
|---|---|
| 404 | その番号の問題が無い |

### 設計の理由

- 「次は何番か」を裏側が返す形にした。問題の一覧を持っているのは裏側なので、一覧に関する判断（末尾の次は先頭、将来の出題順の変更）も裏側に置く。画面は `nextId` をそのまま次の頼みに使うだけでよい。
- 検討した別案は「画面が番号を数え、問題数を別の API で取る」。API が 2 本になり、末尾判定が画面側に漏れるため採用しなかった。

## 3. 回答を評価する

```text
POST /api/evaluate
```

### 頼み方

本文に JSON を入れる。

```json
{
  "questionId": 3,
  "answer": "I'll send it to you by email later."
}
```

| 項目 | 型 | 意味 |
|---|---|---|
| `questionId` | number | どの問題への回答か。裏側はこの番号から日本語の原文を引く |
| `answer` | string | ユーザーの英文。時間切れの場合は空文字（FR-2.4） |

### 返事（200）

```json
{
  "grammar": "問題ありません。",
  "naturalness": "by email より over email の方が口語的です。",
  "better": "I'll shoot it over to you later."
}
```

| 項目 | 型 | 意味 |
|---|---|---|
| `grammar` | string または null | 文法上の指摘。1 文 |
| `naturalness` | string または null | 自然さの指摘。1 文 |
| `better` | string | より自然な英文。1 つ |

- `answer` が空のときは `grammar` と `naturalness` を `null` にし、`better` だけを返す（FR-3.5）。
- 指摘は合計 3 点以内、各 1 文（FR-3.3）。この制約は裏側が LLM への指示文で課す。

### 失敗

| ステータス | いつ |
|---|---|
| 400 | `questionId` か `answer` が無い、型が違う |
| 404 | `questionId` の問題が無い |
| 502 | Ollama に接続できない、または返事を決まった形に整えられなかった |

### 設計の理由

- Phase 6 では Ollama を呼ばず、固定の仮の返事を返す。Phase 8 で中身だけを Ollama 呼び出しに差し替える。画面側はこの取り決めだけに依存するので、差し替えの影響を受けない。
- `GET` ではなく `POST` にしたのは、英文を本文で送るためと、「評価する」という処理を頼む操作だから。

---

## 4. 画面側から見た使い方

```text
起動        GET  /api/questions/1         → 問題を表示、タイマー開始
送信        POST /api/evaluate            → 待機中を表示 → 返事を表示
次へ        GET  /api/questions/{nextId}  → 問題を表示、タイマー開始
```
