# ADR 002: 裏側（Backend）の Web フレームワーク

- 日付: 2026-10-07
- ステータス: Accepted

## Context

ADR 001 で裏側を Node.js + TypeScript で書くと決めた。Node.js には標準ライブラリとして `http` モジュールが含まれており、それだけでも HTTP サーバーは書ける。しかし URL ごとの処理の振り分け、JSON の読み書き、エラー整形などは毎回自分で書くことになる。この「毎回書く部分」をまとめた Web フレームワークを使うかどうか、使うならどれかを決める。

前提:

- 開発者は JavaScript / TypeScript 未経験。エラーの意味が分からず検索する回数が多い段階。
- MVP の裏側は「問題一覧を返す」「英文を受け取り LLM の評価を返す」の 2 つ程度の小さな API。

## Options

| | Express | Hono | Fastify | 素の `http` |
|---|---|---|---|---|
| 位置づけ | 2010 年から続く定番 | 2022 年頃からの新しい枠組み。TypeScript 前提 | 速度重視 | フレームワーク無し |
| 学習資料 | 圧倒的に多い | 少ない | 中程度 | 公式ドキュメントのみ |
| TypeScript との相性 | 後付け。型定義を別途導入 | 最初から TypeScript | 良い | 良い |
| 実務での利用度 | 最も高い | 伸びているが少数 | 中程度 | ほぼ無い |
| 規模感 | 十分 | 軽量 | 軽量 | 最小 |
| 費用 | 0 円 | 0 円 | 0 円 | 0 円 |

## Decision

- **Express** を採用する。
- ただし Phase 4 で裏側を立ち上げる際、**最初の 1 回だけ素の `http` モジュールでサーバーを書き、その後 Express に置き換える**。

## Why

- 初学者が詰まる場所の答えが、15 年分の蓄積としてほぼ全部存在する。「困ったときに答えが見つかる量」を最優先した。
- 実務・求人・既存コードで最も目にする機会が多く、学習の転用先が広い。
- 最初に素の `http` を書くのは、Express が何を省略してくれているかを体感するため。React の前に素の JavaScript で画面を作るのと同じ考え方。

## Trade-offs

- TypeScript の型定義が後付けのため、Hono に比べると型の恩恵が自然には得られない。`@types/express` を別途導入する必要がある。
- Hono や Fastify に比べて設計が古く、性能も劣る。ただし MVP の規模では差が出ない。
- Hono は TypeScript 学習の観点では魅力があり、Phase 11（リファクタリング）以降で比較対象として扱う余地がある。
