# ADR 001: アプリの構成と言語

- 日付: 2026-10-07
- ステータス: Accepted

## Context

MVP に必要な部品は「ブラウザで動く画面」と「LLM に問い合わせる裏側の処理」の 2 つである（product-requirements.md 5 章）。この 2 つをどう組み、どの言語で書くかを決める。

前提:

- 開発者は JavaScript / TypeScript 未経験。Java Silver を保持し、Python を少し触った程度。
- プロジェクトの目的は「仕組みを自分で説明できるようになること」（product-requirements.md NFR-5）。
- 費用は 0 円（NFR-1）。
- 画面側はブラウザで動くため、JavaScript（または TypeScript）以外の選択肢はない。決めるべきは「画面と裏側を分けるか」と「裏側の言語」である。

## Options

### 構成

| | A: React + Vite + 別サーバー | B: Next.js で一体化 |
|---|---|---|
| 構成 | 画面と裏側を別プロジェクトにする | 一つのプロジェクトに両方入る |
| 学べること | Client / Server の境界が物理的に見える | 実務で広く使われる構成そのもの。境界は見えにくい |
| 初心者の負担 | 2 プロジェクトの行き来 | サーバー側で動く部品と画面側で動く部品の区別など、概念が最初から多い |
| 費用 | 0 円 | 0 円 |

### 裏側の言語

| | TypeScript（Node.js） | Python（FastAPI 等） | Java（Javalin 等） |
|---|---|---|---|
| 学ぶ言語の数 | 1 | 2 | 2 |
| Ollama との接続 | HTTP で呼ぶだけ | 同じ | 同じ |
| AI 周辺の道具 | ある | 圧倒的に豊富 | 少ない |
| 型の共有 | 画面と裏側で同じ型定義を使える | 別々に定義し手で合わせる | 同左 |
| 実務での姿 | Web 専業チームで標準 | 「画面 TS + AI 裏側 Python」は AI 製品で多い | 企業システムで強い |

### リポジトリ構成

| | モノレポ | ポリレポ |
|---|---|---|
| 変更の記録 | 画面と裏側の変更を 1 Commit で追える | 2 リポジトリの対応を自分で覚える |
| 型の共有 | 共通フォルダで参照できる | 仕組みが必要で重い |
| 複雑さ | 大規模化すると専用ツールが欲しくなる | 各リポジトリは単純 |

## Decision

- 構成: **A**。画面側は React + Vite + TypeScript、裏側は Node.js + TypeScript。
- 言語: **両側とも TypeScript**。
- リポジトリ: **モノレポ**。`frontend/` と `backend/` の 2 フォルダ。モノレポ用ツール（npm workspaces、Turborepo 等）は導入しない。
- 裏側のフレームワーク（Express、Hono 等）は別の ADR で決める。

```text
instant-english/
├── docs/
├── frontend/    React + Vite + TypeScript（ブラウザで動く）
├── backend/     Node.js + TypeScript（PC 上で動く）
└── README.md
```

## Why

### Next.js ではなく分離構成にする理由

1. **学習目的**: Client と Server の境界を物理的に分けた方が、HTTP で通信している事実が見える。Next.js はその境界を隠す道具であり、仕組みを理解した後に使う方が、何を省略してくれているかが分かる。
2. **裏側の性質**: この裏側は「LLM に問い合わせて 10 秒以上待つ」処理が中心で、画面の配信とは性格が違う。実務でも「画面は Next.js、AI 処理は別サーバー」という分離は一般的。分離しておけば、将来 Python への差し替えや、裏側だけ別マシンで動かすことができる。また、多くの無料ホスティングは 1 リクエストの実行時間に上限があり、長い LLM 処理を画面側と同居させるとクラウド公開時に制約を受けやすい。
3. **学び直しの余地**: 分離構成を先に作ることで、後に Next.js を「同じことをまとめて書ける道具」として比較で理解できる。

### TypeScript 1 本にする理由

- JavaScript 未経験の状態で、非同期処理や型の考え方を 2 言語で並行して学ぶと、どの問題がどの言語由来か切り分けられなくなる。
- 画面側で学んだ `fetch` や `async` の知識がそのまま裏側で使える。
- 「評価結果」などのデータ型を 1 箇所で定義し、両側で使える。
- MVP の範囲（問題を出す、LLM に投げる、結果を返す）では Python の優位はほぼない。Ollama は HTTP で呼ぶだけで、言語による差がない。
- 開発者の志向が「Web アプリの仕組みを理解すること」であり、AI 製品開発ではない。

### Java を選ばない理由

- 言語が 2 つになり、Web 側の学習と分断される。
- 開発者がモダンな言語を学びたいと考えている。

### モノレポにする理由

- 画面と裏側は 1 つのアプリであり、API の形を変えたときに両側を同時に直す場面が頻発する。1 Commit で記録できることが、Git 履歴の分かりやすさに直結する。
- ポートフォリオとして 1 つの URL で全体が見える。
- モノレポ用ツールが解決する問題はまだ発生していないため、導入しない（必要以上に高度なものを入れない方針）。

## Trade-offs

- 2 つのプロジェクトを起動・管理する手間がある。開発時はサーバーを 2 つ立てる。
- Next.js を使った場合に比べ、ページ遷移やサーバー側描画などの機能を自前で考える必要がある（MVP では不要）。
- 将来「音声入力・発音練習」のように AI モデルをアプリ内で直接動かす機能に進む場合、Python の道具の豊富さが効く。その時点で裏側の Python 化を再検討する。分離構成にしてあるため、画面側に影響なく差し替えられる。
- 「なぜ Next.js を使わないのか」と問われることが予想される。本 ADR がその回答となる。

## 関連する将来の検討

- Phase 11 以降: 同じアプリを Next.js で書き直した場合の差分を学習として扱う。
- AI 機能の本格化時: 裏側の Python 化。
